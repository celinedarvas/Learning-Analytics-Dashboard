About this project

An end-to-end analytics case study covering 19,608 student responses across four technical assessment domains.

Source data comes in four different formats: CSV, newline-delimited JSON, Parquet, and YAML. The build pipeline loads each one, cleans them with the rules in the table below, anonymizes every identifier with a deterministic mapping, then runs the analytical queries that produce this self-contained dashboard.

What surprised me

Across all four domains, students spend about the same time on wrong answers as on right ones. Median is 52-54s either way.

The biggest difference is sql_duckdb, where incorrect answers come in about 3s faster than correct ones. In pandas_core it's the opposite: students spend about 2s longer on the questions they miss.

So wrong answers are not a pacing problem. They're a content problem. If I were a teacher looking at this, I'd be working on what's being taught, not how fast students answer.

Recap

What I found

Five things came out of the analysis. Number 3 is the one I didn't expect.

  1. The difficulty levels are calibrated correctly. Average accuracy drops from 69.9% on the easy questions (D1) to 67.8% on the hardest ones (D3). A 2.1-point drop across three difficulty levels means the difficulty system is doing real work. Not so steep that nobody finishes the hard questions, not so flat that difficulty doesn't matter. See chart: Accuracy by difficulty↑
  2. Response time is highest on the first question of each session, then drops. Classic learning-curve shape. Students take longer on the first question because they're getting used to the platform interface, then they speed up over the next few questions. See chart: Response time across sequence position↑
  3. Wrong answers do not take less time than right answers. This was the surprise. I expected wrong answers to be faster (rushing) or slower (struggling). But mean response time is 52-54 seconds on both correct and incorrect answers, across all four subjects. So wrong answers are not a pacing problem. They're a content gap. For a teacher, that changes what to fix. See chart: Mean response time: correct vs incorrect↑
  4. About half the cohort finishes the full curriculum. 248 of 520 students completed all four subjects (47.7%). The other 52.3% completed only 1, 2, or 3 subjects. See table: Learners who completed all four domains↑
  5. 9.3% of sessions get abandoned, evenly across the four subjects. No single subject is the cause. So the abandonment isn't "SQL is too hard" or "data viz is boring." It's something about format, timing, or motivation that applies to all four. See chart: Sessions completed vs abandoned↑

What I learned

Six things I picked up doing this. The skills behind the numbers above.

  1. Real data is never clean. Four source files in four different formats (CSV, NDJSON, Parquet, YAML). Each one needed its own loader. The events file had duplicates and malformed IDs that needed cleaning. The sessions JSON had nested metadata I had to flatten before joining. None of these were ready to use straight from disk.
  2. Window functions replace UNIONs. RANK() OVER (PARTITION BY domain ORDER BY accuracy DESC) gives the top 3 students per subject in one query. Without it, I'd write four separate queries (one per subject) and stitch them together with UNION. Shorter to read and faster to run.
  3. HAVING is for groups, WHERE is for rows. "Students who completed all four subjects" is a property of the group of rows, not of any single row. So it has to go in HAVING after the GROUP BY, not in WHERE.
  4. Right-skewed data needs log bins. The response-time histogram above has log-spaced bins. I tried linear bins first. 95% of the bar was in one tall column on the left and the long tail of slow answers was invisible. Log bins fixed it without changing any data.
  5. Anonymizing PII is not one regex. First pass replaces real student IDs with S-001, S-002, etc. Second pass catches malformed IDs in the raw events file that embed real IDs as substrings. The PII audit only passed after both passes ran.
  6. Build pipelines beat hand-edits. This dashboard is a template HTML, a build script, and a JSON data file. Running the script regenerates index.html. If I hand-edited it every time the data changed, I'd be patching it forever and the dashboard would drift from the source data.
